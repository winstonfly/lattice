## 2. 背景与定位

Tailscale 卖的是管道，没有应用层。用户不想要 VPN，想要"我的片库在哪都能看、能投"。播放器品类有现成的付费习惯（订阅或买断），Apple 生态里尤其成熟。

**一句话定位**：Anywhere Library, Anywhere Screen —— 片库在哪都能播，屏幕在哪都能投，不用开 VPN，不用端口映射。

播放器赛道拥挤（Infuse、Plex、Jellyfin 客户端、VidHub、SenPlayer、nPlayer 等，竞品情况以发布前的实际调研为准）。"更好看的播放器"不构成理由，唯一的楔子是**跨网络**：

- DLNA / AirPlay 只能在局域网内用。
- 竞品没有自己的网络层，远程访问依赖用户自己配 VPN、端口映射或第三方隧道。
- 我们有 lattice，能把"远程访问"和"跨网投屏"做成应用内的默认能力。

### 为什么必须用"内嵌"而不是"系统 VPN"

播放器场景下，内嵌式 lattice（[嵌入式 SDK 设计](./2026-09-22-apple-embedded-sdk-design.md)）比系统 VPN 更合适：

1. 不弹系统 VPN 授权，不占系统"VPN"列表，用户不会觉得"看电影要开 VPN"。
2. iOS 同一时刻只有一个活跃 VPN。已在用 Tailscale / WireGuard / 公司 VPN 的用户不能再开第二个，内嵌方案与它们共存。
3. 审核形态更简单：App 不是 VPN 应用，不涉及 Network Extension 的额外审核。

代价（已在嵌入式 SDK 设计中接受）：只有本 App 自己能走 overlay，拿不到系统级流量拦截，iOS 后台保不住连接。播放是前台行为，这个代价可以接受；后台下载类需求不在本期范围。

## 3. 目标与非目标

**目标**

1. 用户在任意网络下，打开 App 就能播放自己家里或 NAS 上的片库，首帧时间和家里局域网内接近。
2. 用户能把自己片库里的内容，从任意位置的手机，投到任意位置装有接收端的电视，媒体流走 overlay 直连，不经过第三方云。
3. 服务端接入摩擦足够低：从安装 App 到第一次跨网播放不超过 5 分钟，服务端步骤不超过 2 步。
4. 基础播放体验达到品类的"入场券"水平，不因缺格式、缺字幕、缺 HDR 而被直接劝退。

**非目标**

- 不做国内首发（网盘来源合规与上架风险留待后续单独评估）。
- 不做 Windows / Android 手机播放器（Android TV 仅作投屏接收端）。
- 不接入流媒体订阅服务，不做 DRM 内容播放。
- 不替代 Jellyfin / Plex / Emby：播放器对来源保持中立，Reflux 只是其中一个来源。
- 不对 lattice 本身收费，也不在本期做企业侧功能。

## 4. 分层架构

```
产品层   播放器 App（iOS / tvOS / macOS）    投屏接收端（tvOS / Android TV / macOS）
            │                                  │
引擎层   PlayerCore / PlayerKit（开源核心 + 闭源 Pro）      LatticeCast 协议
            │                                  │
底座层   lattice 嵌入式 SDK（shim.Server：零权限 Dial/Listen）   FERRY 中继 / ICE 直连
            │
来源层   Reflux（自家）  Jellyfin / Emby / Plex / WebDAV / SMB（服务端需运行 lattice agent）
```

分界原则：

- **底座层免费开源**，只提供"两个节点之间的加密连接"，不知道有播放器。
- **引擎层**沿用 PlayerCore 的划分：内核拥有传输、解码、状态机；壳拥有业务和 UI。
- **产品层**拥有业务：来源管理、元数据、跨网发现、授权、Pro 付费。

## 5. 核心场景

### S1 跨网播放（P1）

App 内嵌 lattice，服务端旁边跑一个 lattice agent（Reflux 用户随 docker-compose 自带 sidecar，Jellyfin / Plex 用户用一行命令起一个 agent 容器）。App 通过 overlay 地址访问来源。传输优先 ICE 直连，失败时走 FERRY 中继，用户无感。

### S2 跨网投屏（P2）

手机在外面（或在朋友家），电视在家里（或反过来）。

1. 手机发现同一 lattice 网络内的接收端（沿用 LatticeCast 的发现与协议）。
2. 手机把"播放这个媒体"的指令发给电视，电视端直接通过 overlay 从来源拉流，手机不做转发。
3. 授权：接收端只接受同一网络内已认证节点的指令，沿用 LatticeCast 现有的 Bearer Token，并在 P2 增加基于节点身份的校验。

这是 DLNA / AirPlay 做不到的，也是本产品区别于竞品的核心点。

### S3 分享（P3）

用一个邀请链接把某个片库（或某个合集）限时、限权限地分享给朋友，对方装 App 后零配置可用。依赖 lattice 侧的节点邀请与到期机制，具体设计另写 spec。

### S4 自然语言入口（P4）

lattice-copilot 作为可选入口，"把上次那部电影投到卧室电视"。它不属于楔子，保持原有设计不变，在 P1-P3 稳定后接入。

## 6. 入场券清单（基础体验对标）

跨网能力再强，基础播放不达标也会被直接劝退。以下为 P1 上架前必须满足的最低集合，每项需对照 PlayerKit 现状做一次审计（当前能力未逐项核实）：

- 容器 / 编码：MKV、MP4、HEVC、H.264，AV1（视设备硬解而定）
- 字幕：SRT、ASS/SSA、PGS、外挂字幕、字幕样式
- 音频：多音轨、EAC3 / DTS / TrueHD / Atmos 直通（Pro）
- 视频：HDR10、Dolby Vision（需确认 PlayerKit 的支持程度）、HDR→SDR 色调映射
- 元数据：TMDB 海报 / 简介 / 演职员，自动匹配
- 进度：多设备续播同步；Trakt 同步（视调研而定）
- tvOS 遥控器操作体验、大屏 UI

Reflux 已有 iOS / macOS / tvOS 三端 App 与 StoreKit 配置，P1 起点是"在现有 App 上补齐并改造"，不是从零开始。

## 7. 商业模式（初稿）

- **App 免费下载**，基础播放和局域网来源免费。
- **Pro（订阅 + 买断，走 StoreKit）**：跨网投屏、HDR / Atmos 直通、多设备同步等。价格锚点需要对照海外同类产品做一次实际调研后再定，本文不写具体数字。
- **lattice 底座免费开源**，用户可自建 FERRY 中继。
- **官方中继**：提供公平使用额度（含在 Pro 内），超额或商用另议。这是成本项，不是主要收入来源。

修订说明：copilot spec 里"relay LLM token 配额是付费钩子"的设定需要随之调整，改为挂在 Pro 权益下。该调整不在本文范围内，评审通过后同步修改 copilot spec。

## 8. 路线与验收

各阶段进入实现前先写自己的 spec 和 plan，这里只定义顺序和验收口径。数值型目标都是初始设定，需在测得基线后修正。

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 前置门 | 连通性可靠 + 嵌入式 SDK 性能可行 | 见 §8.1 |
| P1 跨网播放 MVP | iOS + tvOS 播放器内嵌 lattice，播放 Reflux / Jellyfin 来源；入场券清单达标 | 从安装到首次跨网播放 ≤ 5 分钟；直连下跨网首帧接近局域网体验；切网（wifi↔蜂窝）恢复 < 30 s（沿用已接受的标准） |
| P2 跨网投屏 | 接收端（tvOS / Android TV）内嵌 lattice；手机端发起；节点身份授权 | 跨网络一键投屏成功率与首帧时间达标（指标 P2 spec 内定） |
| P3 分享 | 邀请链接、限时限权限 | 朋友端零配置可用 |
| P4 入口 | copilot 接入 | 沿用 copilot spec |

### 8.1 P0 前置门（不通过则不进入 P1）

1. **连通性可靠**：FERRY 中继 P1（非阻塞转发队列）和 make-before-break 升级（ADR-0007）落地；relay 不再出现"从未转发过一个包"这类问题。跨网播放的体验完全建立在这上面。
2. **吞吐可行性验证（最大技术风险）**：嵌入式 SDK 是用户态 WireGuard + gVisor netstack，4K remux 码率可达 80–100 Mbps 甚至更高。需要在真实设备（至少 Apple TV 和一台中端 iPhone）上做一次 spike：测直连和中继下的稳定吞吐与 CPU / 内存占用，确认能支撑目标码率。若不可行，需要回到"系统级 NE"或降级为"仅支持转码后的低码率远程播放"，这会改变 P1 的形态，因此必须先验证。
3. **分发形态确认**：见 §9 风险 3。

## 9. 风险与开放问题

1. **服务端接入摩擦**：远程访问要求来源端运行 lattice agent。Reflux 用户可随 compose 自带，但 Jellyfin / Plex 用户多一步。这是转化率的关键，P1 需要把"一行命令 + 自动配对"做到极简。
2. **与 Infuse 的体验差距**：Infuse 在细节体验和格式覆盖上已很成熟。我们的差异只在跨网，基础体验不能明显落后（§6），否则跨网优势不足以让用户迁移。
3. **许可与商店分发的冲突**：PlayerCore spec §六写明"FFmpeg 以 LGPL 动态链接，macOS 不走 Mac App Store"。海外优先意味着 iOS / tvOS 必须走 App Store，而 iOS 上动态框架与 LGPL 重链接义务的处理需要专门的许可审查。此项必须在 P1 前得出结论，可能反过来改变引擎层的后端选择。
4. **出口合规**：WireGuard 属于加密功能，App Store Connect 需要完成出口合规声明（包含美国 BIS 的自我分类流程），需在首次提交前确认所需材料。
5. **内容合规**：播放器对来源保持中立，不内置、不指向任何侵权来源；保留 DISCLAIMER。115 等区域性网盘来源不进入海外版首发。
6. **中继成本**：官方中继带宽是真实成本，公平使用额度的具体数值需要在拿到真实用量后再定。自建中继选项要在文档里说明。
7. **未验证的前提**：嵌入式 SDK 设计本身状态为"未验证"（见其 §一）。本文路线的 P1 依赖它，因此 §8.1 第 2 条不是可选项。
